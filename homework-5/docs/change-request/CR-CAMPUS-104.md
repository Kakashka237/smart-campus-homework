## 1. Описание релиза и бизнес-цель

**Что меняется.** Колонка суммы чека `Receipts.Price` переименовывается в `Receipts.Amount`.
Переименование выполняется по паттерну **Expand and Contract** в три фазы, без простоя сервиса.
Дополнительно в сервис добавлены теги OpenTelemetry `jira.issue` и `campus.transaction_id`
для сквозной трассировки платежей.

**Бизнес-цель.**
- Привести модель данных к единому словарю платёжного контура: в API терминалов оплаты,
  в выгрузке в 1С и в банковском эквайринге сумма операции называется `Amount`. Колонка `Price`
  путала разработчиков и аналитиков: «цена блюда» и «сумма чека» — разные величины (в чеке
  может быть несколько блюд и скидка по студенческому).
- Сократить время разбора инцидентов по оплате: по `campus.transaction_id` и `jira.issue`
  дежурный находит трассу конкретного чека и задачу, в рамках которой менялся код.
- Столовая работает с 08:00 до 20:00, поэтому остановка оплаты недопустима. Переименование
  «в лоб» (`ALTER TABLE ... RENAME COLUMN`) сломало бы работающие экземпляры v1.8.x и отчёты.

**Обоснование времени.** По данным мониторинга за последний месяц:
- пик нагрузки — 12:30–14:30 (большая перемена, до 40 оплат в минуту);
- столовая и буфеты закрыты с 20:00 до 08:00, ночью идут только служебные запросы
  (сверка с банком в 01:00, выгрузка в 1С в 05:00);
- минимум трафика — **02:00–04:00**, меньше 1 запроса в минуту.

Окно выбрано между сверкой с банком (01:00) и выгрузкой в 1С (05:00), чтобы миграция
не пересекалась с этими процессами. Выходные не подходят: в субботу работает буфет
для заочников, а дежурный DBA выходит в будни. Вторник выбран, чтобы в понедельник
успеть провести финальную проверку на стенде staging.

## 4. План отката (Rollback Plan)

**Критерии отката** (любой из пунктов):
- Sanity-тест не прошёл;
- доля ошибок 5xx выше 2 % в течение 5 минут;
- latency p95 больше 1 с;
- найдены чеки, у которых `Amount` и `Price` различаются.

**Действия при откате фазы 1:**

```bash
# 1. Откатить приложение на предыдущую ревизию (v1.8.3)
kubectl rollout undo deployment/canteen-api -n campus

# 2. Дождаться завершения отката
kubectl rollout status deployment/canteen-api -n campus

# 3. Проверить, какая версия работает
kubectl rollout history deployment/canteen-api -n campus
```

Откат схемы БД **не требуется**: v1.8.3 не знает о колонке `Amount` и продолжает работать
с `Price`, а триггер синхронизации сохраняет согласованность данных. При необходимости
колонку можно удалить: `ALTER TABLE "Receipts" DROP COLUMN "Amount";`.

**Откат фазы 2** — не требуется: данные копируются, исходная колонка не изменяется.

**Откат фазы 3** — только восстановление колонки `Price` из резервной копии, поэтому фаза 3
выполняется отдельным CR после 7 дней стабильной работы.

Время отката приложения — около 2 минут. Решение об откате принимает дежурный инженер.
